# ミューテーションテストの調査・修正

目的は実装の簡潔さ、テストの検出能力と保守性の改善。CI成功、スコア向上、warning件数の減少だけでは完了としない。

## 全件を取得して判断する

1. まず既存artifactとローカル結果から全対象の調査結果を取得する。結果がない対象や変更の影響を受ける対象は、ローカルで `pnpm mutate:audit <対象>` を実行する。修正のたびに全10対象を再実行しない。CIの全件調査は初回、大きなテスト整理、計測設定の変更など、全体の比較が必要な節目にまとめて使う。`node scripts/mutation/summarize.mjs <取得先>` で集約する。Job Summaryの抜粋やログの末尾だけで調査範囲を決めない。`summary.json` の全 `findings` を読み、対象欠落・古い実行結果・調査未完了を0件と混同しない。
2. survived、noCoverage、duplicates、subsumed、noKills、timeout、incompleteを分け、各項目のID、変異位置、関係するテストを確認する。timeoutやmoduleロード失敗はテスト単位の比較が成立した証拠にはならない。
3. 各項目について実装・テスト・仕様・呼び出し側を読む。同じ原因の項目はまとめて調査してよいが、PRコメントでの判断は全IDを対象とする。根拠なしに分類単位で一括承認しない。
4. survivedでは不要な実装の削除・条件の簡略化を先に検討する。必要な仕様の検証が欠けている場合にテストを改善する。warningを消すためだけにテストを増やさない。
5. duplicates・subsumedでは入力と期待値を比較し、重複した検証を削減する。kill setの一致だけでは固有の仕様が不要になったとは判断できない。nullと空文字列、成功と失敗、異なるAPIの契約などを残す必要がある場合は理由を記録する。
6. noCoverage・noKillsでは利用箇所と仕様を確認する。不要コードか、未検証の契約か、変異演算子の限界かを区別する。timeout・incompleteはログも確認し、変異が無限待機を作るケースと実行環境の障害を分ける。

## 計測の妥当性を確かめる

- 急なnoCoverageの増加、moduleロード失敗、timeoutは、同じ変異と関係するテストの限定実行でも確認する。変換キャッシュ、ソースの実体パス、初期化時間を含まない実行予算の問題を、実装の不要・検証不足と混同しない。限定実行は全対象の集約を代替しないため、比較時には対象ソースと実行テストの集合も確認する。
- テストが途中失敗しても、未消費のmockのOnce応答や外部フィクスチャが後続ケースへ残らないことを確認する。正常系だけで成功する後始末ではkill setが混ざる可能性がある。
- 実行中の対象の実装・テストは変更しない。変更した場合は、以前の結果を修正後の結果として扱わず、影響する範囲を再実行する。

## 修正・再評価

- PRコメントに項目IDごとの判断（修正・維持・保留）、根拠、実装・テストの参照を記録する。判断台帳をリポジトリに追加しない。未対応は未対応として理由を残し、保留を「維持」と書き換えない。
- 修正箇所の通常テストと対象のmutationを実行する。全件調査を繰り返す必要がある場合は変更をまとめてから実行し、実行中の調査をpushで中断しない。
- 修正中は関連する変異・テストの限定実行を使い、変更をまとめた段階で影響する対象の全件を再実行する。テスト変更はduplicates・subsumedの関係にも影響するため、変更行の変異だけで最終判断しない。全対象の集約では各結果の計測時点と再利用の根拠を確認し、影響範囲が判断できなければ再計測する。古い結果を最新コミットの全件計測と報告しない。消えた項目だけでなく、新規項目・変更された項目・残存項目も再評価する。過去の記録を新しい結果へ無条件に流用しない。
- 全対象の実行結果が揃い、すべての検出項目に根拠付きの対応要否判断があることを確認する。未取得・実行中断された対象や未判断項目がある間は作業完了と報告しない。timeout・incompleteを維持する場合も、計測できない理由と判断根拠を明示する。
- 最終報告には削減・修正内容、再実行の範囲、未対応項目と理由を含める。残る項目は個別IDとPRコメントから追跡できるようにする。

## 実行と結果の取得

対象は `scripts/mutation/projects.mjs` の10対象。`pnpm mutate:audit <対象>` は対象を省略すると利用可能な名前を表示する。web serverのローカル実行には127.0.0.1:54321の認証エミュレータが必要。CIはsupa-emuを起動する。

```sh
pnpm mutate:audit domain
node scripts/mutation/summarize.mjs mutation-audit
```

JSON・HTMLの出力先は `mutation-audit/<対象>/`。CIの対象別artifactにはログも含まれ、保存期間は30日。全対象の構造化データは `mutation-audit-summary` artifactの `summary.json`、完全な表示は `summary.md` から取得する。Job Summaryがサイズ制限でID一覧やartifactへの案内になっている場合も、JSONから全項目を取得する。

通常CIは差分の回帰検出に使い、既存のcritical判定とstdの閾値を維持する。全件調査の `Mutation audit` はスコアの閾値を設けず、手動実行または調査スクリプト・設定・ワークフローを変更するPRの作成時に起動する。PR更新時には自動で再実行しない。

## 集約と判断記録の形式

- レポート欠落・形式不正は「—」、有効な計測で検出がない場合は0件。`partial` は未完了や旧コミットの結果を含む。`complete` は計測の状態であり、判断完了を意味しない。
- survived・noCoverage・timeoutは変異数、duplicatesはテスト群数、subsumed・noKillsはテスト数。incompleteは未比較変異や実行警告の件数。
- 各項目のIDから変異位置、元の式と置換後の式、関係するテストIDを取得できる。duplicates・subsumedにはkill setの変異の内容も含まれる。
- 共通の根拠はPRコメントでまとめてよいが、該当する全項目IDと計測コミット・artifactを明示する。修正後は対応状況と未対応理由を追記する。集約JSONは検出結果を示すものであり、判断完了を自動判定しない。
- timeout・incompleteの理由を判断しても、未実施の比較が完了したことにはならない。

## 計測の範囲

テスト用ヘルパーとStorybookのstoriesは変異対象から除く。Storybookのブラウザ実行とE2EはこのVitest adapterの調査に含まれず、通常のcomponentテストとE2Eで検証する。TypeScript 7との互換性により、変異ごとの型チェックは無効。
