# React の非同期 UX と API の選定

対象: [Issue #1094](https://github.com/geek-beyond/trend_diary/issues/1094)

## 決定

| 対象 | 採用する仕組み | 理由 |
| --- | --- | --- |
| 記事一覧 | SWR `keepPreviousData` / `isValidating` | 通信中に旧一覧を維持できる。応答に取得条件の識別子を持たせ、表示中のページ番号と条件変更を区別する。フィルタは即時更新し、旧結果の操作は一時停止する。失敗しても旧結果と失敗の案内を残す。 |
| 未読消化 | 既存のローカルキューの楽観更新 | 次の記事・残件数を応答前に更新し、失敗時は操作前のスナップショットに戻す。同一イベント内の連打は ref、表示上の無効化は state で防止する。完了演出と次バッチ取得は API 成功後に行う。 |
| 統計 | SWR の日付別キーと loading | 日付の選択は即時に反映し、グラフを維持する。日別詳細全体をスケルトンに置き換え、旧日付のサマリーやページ番号を新日付の結果として見せない。 |
| ショートカット | `useEffectEvent` | `keydown` の購読を維持したまま、最新の開閉状態・モバイル状態で操作する。 |
| モバイル判定 | `useSyncExternalStore` | フックごとに同じ `MediaQueryList` をスナップショットと購読に使う。SSR のスナップショットは従来どおり false。 |

未読消化ではフォーカス・再接続時の自動再検証を停止し、消化途中のローカルキューを応答で巻き戻さない。次バッチと明示的な再試行で同期する。再試行が同じ内容の応答でも同期できるよう参照同一性で比較する。メディア変更時は消化セッションを再マウントし、別条件のキューや進行中の処理と混ぜない。

## 認証フォームの比較

現行の共通 `useAuthSubmit` は Zod 検証、Turnstile hidden input の読取り、API エラーの変換、成功時の処理をまとめ、ログイン・登録の表示コンポーネントが DOM イベントを `FormData` に変換している。

| 観点 | 現行 | `useActionState` + form action 案 |
| --- | --- | --- |
| 状態 | `isSubmitting` / `errors` / `formError` の3つ | エラーを1つの結果に集約し pending は React に任せられる。ただし成功後の送信禁止には成功状態が別途必要 |
| 責務・コード量 | 共通 hook と各フォームの短い submit ハンドラ | 各フォームのイベント変換は削減できるが、結果型・成功状態・入力値保持の処理が必要 |
| 失敗後の入力値 | 非制御 input がそのまま保持する | action がエラー結果を return して正常終了するとフォームがリセットされるため、入力値の制御または別の復元設計が必要 |
| 成功時 | SWR セッション更新と遷移の間もボタンを無効にする | pending だけでは action 終了後に再度有効になるため、成功状態との合成が必要 |
| テスト負荷 | 既存のログイン・登録 hook と Storybook | 既存の検証に加え action の実行文脈、入力値復元、pending 終了後の送信禁止を検証する必要がある |

今回は移行しない。`useFormStatus` もボタンを別コンポーネントに分ける必要があり、入力欄の無効化には親の状態が必要なため、現行の props を十分には減らせない。Zod・CAPTCHA・エラー表示・成功時のセッション更新と遷移は既存実装を維持する。

## `useDeferredValue` の試行

Node.js 26.13.0、React 19.3.1、Vitest 5.0.5 / jsdom で、実際の `useArticles` と `TrendsPage` を React `Profiler` で計測した。20件の一覧を表示し、メディアを変更、レスポンスを保留して旧一覧を確認した後、別IDの20件を返した。SWR のデータ全体（ページ・取得条件を含む）を遅延させる案と、SWR のデータ保持だけの案を比較した。

| 案 | フィルタ変更から新一覧確定までのコミット数 | 各コミットの actualDuration（参考、ms） |
| --- | --- | --- |
| `keepPreviousData` + `useDeferredValue(data)` | 3 | 21.94 / 3.43 / 35.43 |
| `keepPreviousData` のみ | 2 | 5.08 / 9.46 |

どちらも選択状態は最初のコミットで変更され、応答前は旧一覧・旧ページを保持した。追加の遅延はコミットを増やし、この構成では応答性の改善を確認できなかったため採用しない。計測は各案1回の開発用 jsdom 環境で、Compiler を通した本番ビルドや実機ブラウザの入力遅延・描画速度を示すものではない。時間差自体を性能改善率とは扱わない。今後、実機で高コストの同期描画を確認した場合は再評価する。

## その他の API

- `useTransition`: URL 更新を囲むだけでは SWR の通信待ちを表現できず、同期描画の優先順位を変更する必要性も今回確認できなかったため採用しない。
- `useOptimistic`: 現在のキューと残数に加えて action の基底状態・再同期が必要になる。連続操作を禁止する仕様では既存キューのスナップショットによる復元で十分なため採用しない。
- `use` / `Activity`: 既存 SWR のキャッシュ・再試行や React Router の画面管理を置き換える具体的な利点がないため採用しない。

## 検証範囲

回帰テストで、旧一覧保持、条件の即時反映、旧ページ維持、遅い旧リクエストの無視、失敗と再試行、未読の即時消化と復元、連続操作の抑止、同期的な外部記事オープン、成功後のみの完了演出、次バッチ取得失敗、統計の詳細スケルトン、キー購読の継続と解除、モバイルの初期値とブレークポイント切替を確認する。既存の認証テストも継続する。
